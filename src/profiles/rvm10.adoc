== RVM10 Profiles

NOTE: This profile is under development and is not ratified.  The
contents of this chapter are a draft and subject to change.  Not for
implementation.

The RVM10 profile family targets microcontroller-class processors,
with the goal of simplifying the demands on the software ecosystem,
particularly toolchains and library suppliers.

It is explicitly a non-goal of RVM10 to provide maximum flexibility
for microcontroller developers.  Maximum flexibility can already be
achieved using individual RISC-V extensions.  The goal of RVM10 is to
mandate a common set of standard extensions to simplify software
support and reduce fragmentation across MCU vendors.

RVM10 reflects the current state of the RISC-V ISA and the needs of 
mid-range and high-end embedded applications in industrial control, motor
drives, automotive ECUs, IoT gateways, and similar workloads.

This initial version of the RVM10 family specifies only unprivileged
ISA features (RVM10U32).  ISA features for supervisor-mode execution
are planned for a subsequent phase that will define RVM10S32.
Machine-mode behavior, interrupt handling and other platform-specific
requirements are defined in the companion microcontroller subsystem
specification, not in this profile.

=== RVM10U32 Profile

The RVM10U32 profile specifies the ISA features available to
unprivileged execution environments in 32-bit microcontroller-class
processors.

==== RVM10U32 Mandatory Base

RV32I is the mandatory base ISA for RVM10U32, and is little-endian.
As per the unprivileged architecture specification, the `ECALL`
instruction causes a requested trap to the execution environment.

NOTE: An ultra-minimal profile based on RV32E is out of scope for
RVM10 and may be specified separately in the future.

Misaligned loads and stores might not be supported.

NOTE: Software should not assume that misaligned loads and stores will
work, or that all misaligned loads and stores will necessarily cause a
trap.

==== RVM10U32 Mandatory Extensions

The following extensions are mandatory in RVM10U32:

- extlink:m[] Integer multiplication and division.

NOTE: Mandating divide instructions in addition to multiplies (rather
than only mandating ext:zmmul[]) adds modest area but reduces
optionality.  RVM10 targets mid-range and high-end MCUs, not the
smallest possible microcontrollers.

- extlink:b[] Bit-manipulation instructions (comprising ext:zba[],
  ext:zbb[], and ext:zbs[]).

- extlink:zce[] Code size efficiency extensions.  On RV32 with F,
  ext:zce[] includes ext:zca[], ext:zcb[], ext:zcf[], ext:zcmp[], and
  ext:zcmt[].  On RV32 without F, ext:zce[] includes ext:zca[],
  ext:zcb[], ext:zcmp[], and ext:zcmt[].  The `jvt` CSR must be
  writable and support the jump-table mode.

NOTE: ext:zce[] includes ext:zicsr[].

- extlink:zicsr[] Control and Status Register access instructions.

- extlink:zifencei[] Instruction-fetch fence.

- extlink:zicond[] Integer conditional operations (`czero.eqz`,
  `czero.nez`).

NOTE: ext:zicond[] is also mandatory in RVA23.

- extlink:zihintpause[] Pause hint for spin-wait loops.

NOTE: PAUSE is a HINT, so implementations are allowed to treat it as a
NOP.  Its presence in the mandatory set signals that implementations
should optimise spin-wait behaviour where practical.

- extlink:zicbop[] Cache-block prefetch operations.

NOTE: These are hints, so implementations are allowed to treat them as
NOPs.  Zero gate cost on implementations without caches.

- extlink:zicbom[] Cache-block management operations (clean, flush,
  invalidate).  Required for correct data visibility between the CPU
  and non-coherent agents such as DMA controllers and peripheral
  engines.  The instructions must be supported on all memory regions
  with cacheable and coherent PMAs, and must not raise an exception on
  such regions.

NOTE: This profile does not require an implementation to have caches.
The requirement is expressed against memory attributes rather than
against the presence of a cache, so an implementation without caches
satisfies it: with no cached copies to write back or invalidate, the
architectural effect of a clean, flush or invalidate operation is
already achieved.  Software can therefore issue cache management
operations unconditionally on any compliant implementation.

- extlink:zicboz[] Cache-block zero operations.  Provides fast zeroing
  of memory regions, avoiding the read-for-ownership overhead of store
  loops.

NOTE: Unlike the other cache-block operations, ext:zicboz[] has an
architectural effect on memory: `cbo.zero` stores zeroes to the
addressed block.  It is not a hint and cannot be implemented as a NOP,
including on implementations without caches, where it is realised as a
store of zeroes to the block.

- extlink:zicntr[] Base counters and timers (`cycle`, `time`,
  `instret`).

NOTE: Real-time software uses these counters to measure execution
time, for example the length of critical sections and task switches.

==== RVM10U32 Optional Extensions

NOTE: The optional-extensions set for RVM10U32 is still under TG
discussion.  The subsections below define the structural categories;
individual options will be added as the draft matures.

===== Localized Options

There are no localized options in RVM10U32 yet.

===== Development Options

- extlink:zilsd[] Load/store pair instructions for RV32.

- extlink:zclsd[] Compressed load/store pair instructions for RV32.
  ext:zclsd[] requires ext:zilsd[].  It has overlapping encodings
  with ext:zcf[] and cannot be implemented together with ext:f[],
  because ext:zce[] includes ext:zcf[] when ext:f[] is present.

NOTE: Load/store pair instructions move 64-bit values with a single
instruction on RV32, which helps code that works with 64-bit integers
or with double-precision values held in integer registers.  They are
listed as development options because they are expected to become
mandatory in a later RVM profile.

===== Expansion Options

- extlink:zalrsc[] Load-reserved and store-conditional instructions.

- extlink:zaamo[] Atomic memory operations.

NOTE: Atomic instructions are not in the mandatory set.  Software on
single-hart microcontrollers commonly protects critical sections by
masking interrupts and has no need for them.  They become necessary
on multi-hart implementations, where they are used for locks and for
communication between harts.  An implementation that provides both
ext:zalrsc[] and ext:zaamo[] provides the A extension.

- extlink:f[] Single-precision floating-point.

- extlink:d[] Double-precision floating-point, which requires
  extlink:f[].

NOTE: Hardware floating point is deliberately not in the mandatory
set.  Many microcontrollers in the target range implement floating
point in software, and mandating it would exclude them.  Naming
ext:f[] and ext:d[] as options means implementations with and without
hardware floating point are both conformant, and toolchains know
precisely which variant they target.  Where ext:f[] is present,
ext:zce[] includes ext:zcf[] as stated above.

===== Transitory Options

There are no transitory options in RVM10U32.

==== RVM10U32 Recommendations

Implementations are strongly recommended to raise illegal-instruction
exceptions on attempts to execute unimplemented opcodes.

=== RVM10S32 Profile

NOTE: RVM10S32 is a placeholder for the supervisor-mode profile and is
not specified in this draft.  Its mandatory and optional extensions
are subject to TG discussion.
